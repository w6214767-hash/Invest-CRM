## Сопоставление с действующим Штабом

- Исходники Штаба найдены: каталог `owner-hq/` в репозитории `w6214767-hash/espocrm`; локально также отдельный репозиторий owner-hq в проекте.
- Прямой GET `https://shtab.ugsdom.ru/health`: 200, версия 2.0.0, release `ce56cfe076f1ec4ae8e8efed5d16f39704755ffe` на момент проверки.
- Прямой discovery `https://login.ugsdom.ru/.well-known/openid-configuration`: 200, issuer `https://login.ugsdom.ru`, PKCE S256. `amr`/`sub` поддерживаются; `investscan_roles` в списке claims отсутствует. Это не проверка закрытой конфигурации конкретного клиента.
- Код Штаба требует точного issuer/subject собственника и `mfa pwd otp`. Текущий PR ранее требовал нестандартный claim ролей. Добавлен необязательный owner-only режим с `OIDC_OWNER_SUBJECT` и `OIDC_REQUIRED_AMR=mfa pwd otp`, без назначения роли по email и без передачи cookie между приложениями. При заданном subject роли других пользователей не дают доступ. Прежний режим ролей сохранён для будущего расширения.
- `invest.ugsdom.ru` пока не разрешается локальным DNS. Это проектный адрес; действующий вход и live-приложение не заявляются готовыми.

## Конкретный комплект подключения

1. Выбрать существующий VPS2 и подтвердить его ресурсы, reverse proxy и свободный loopback порт 8093. Существующие сервисы Штаба/CRM сохраняются.
2. На сервере создать отдельный confidential OIDC client по `deploy/investscan/authelia-client.yml.example`; отдельный случайный секрет, exact callback, PKCE S256 и two_factor. Проверить конфигурацию установленной версией Authelia перед применением. Пример — фрагмент клиента, не замена файла провайдера.
3. Получить из IdP точный subject собственника для этого клиента. Не предполагать совпадение pairwise subject между разными клиентами. Заполнить серверный `.env`: issuer, client id/secret, `OIDC_OWNER_SUBJECT`, required AMR, APP_URL, отдельные SECRET_KEY/POSTGRES_PASSWORD. Секреты не копировать в Git, отчёт или frontend. При смене owner-only/role policy отозвать существующие сессии ИнвестСкана до открытия нового режима: старые строки сессий не хранят MFA assurance.
4. Настроить DNS/HTTPS для выбранного адреса. Проверить сертификат и сеть. Пока это не выполнено, кнопка работающего модуля не должна обещать доступность.
5. Выпустить ровно одобренный SHA отдельным стеком `deploy/investscan/compose.yml`; миграция должна завершиться до старта API. Старый compose с портом 80 не запускать. Автозапуск прежнего deploy.yml по main удалён; новый ручной workflow только собирает архив точной ревизии и контрольную сумму, сервер не изменяет.
6. В Штабе уже существует сохраняемое поле `development_url` проекта ИнвестСкана. До выпуска оно может ссылаться на PR; после приёмки — на рабочее приложение. Для отдельной основной кнопки запуска требуется изменение карточки платформы в репозитории Штаба; этот PR относится только к Invest-CRM и не выдаёт такую кнопку за опубликованную.
7. Приёмка: переход из существующей сессии Штаба → OIDC клиента ИнвестСкана → карточка по глубокой ссылке; отказ чужому subject и без MFA; проверка CSRF/истечения/отзыва; создание и повторный импорт; сохранение цены; устаревший расчёт; отказ покупки без проверок; backup и восстановление в новую БД; перезапуск и сверка числа объектов. Только после этого указывать live-ready.

## Состояние подготовленного пакета

Расширенная реализация PR №5 сохранена целиком. Дополнение касается совместимости первоначального owner-only входа с провайдером Штаба, тестов и подготовки релиза. Реальные источники площадок, OCR, геопроверка, доставка сообщений, бухгалтерия и синхронизация EspoCRM остаются следующим функциональным этапом. Локальные проверки выполняются на синтетической отдельной базе; production-данные не изменяются.

Официальные основания: https://www.authelia.com/configuration/identity-providers/openid-connect/clients/ и https://www.authelia.com/integration/openid-connect/openid-connect-1.0-claims/ .
